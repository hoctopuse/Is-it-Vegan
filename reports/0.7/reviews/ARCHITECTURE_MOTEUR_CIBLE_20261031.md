# Place du moteur : conserver la bibliothèque JVM et la nommer analysis-core

État inspecté le 31 octobre 2026, HEAD `ee499e53413769a42f8459587742409b24b7ee70`. Décision proposée, aucune migration effectuée. Voir [suivi et lots](SUIVI_AUDIT_ET_PLAN_ACTION_20261031.md).

## Responsabilité actuelle établie

`settings.gradle.kts` inclut `:app` et `:mutation-core`. `app/build.gradle.kts:37` déclare une **dépendance de production** `implementation(project(":mutation-core"))`. Le second module applique `java-library` et Kotlin JVM, toolchain/cible 17, JUnit en test seulement. Aucune dépendance Android, plugin PIT ou logique de mutation dans son Gradle courant. Le nom décrit son origine, pas son rôle réel.

Chaîne active inspectée : manifest MAIN/LAUNCHER → `app/.../MainActivity.onCreate` → `OcrFirstScreen` → `OcrFirstScreenContent.analyse` → façade Android `VeganAnalyzer.analyzeWithDiagnostics` → `IngredientAnalysisService` dans `mutation-core/.../VeganAnalyzer.kt` → segmentation/sections → prétraitement/arbre/tokens → lexique/matcher/origine/inconnus → résultat/diagnostics → `VerdictExplanationFormatter` Android → UI/snapshot/export.

Chargement : `AndroidIngredientKnowledgeLoader` lit les trois assets avec Context ; `IngredientKnowledge.fromJson` et MiniJson parsènt les textes en JVM ; le service reçoit la connaissance. Revue : `OcrProcessor` → façade → `IngredientAnalysisService.generateMultilingualAlignment` → générateur JVM → `MultilingualAlignmentReview` Compose. Ces appels établissent un raccordement, les tests JVM exécutés établissent des comportements moteur ; ils ne prouvent ni UI réelle ni photo de bout en bout dans cette passe.

## Comparaison des cibles

Comparaison fondée sur la configuration locale et les contraintes observées, sans affirmation de compatibilité de plugins non essayés.

| Axe | Garder le module JVM et le renommer `:analysis-core` | Déplacer le moteur dans `:app` |
|---|---|---|
| Sens du nom | Exprime sa fonction : analyse, pas outil de test. | Nom core disparaît mais frontière métier moins explicite ; package/dossier dédié nécessaire. |
| Gradle | Changer include, répertoire/projet, dépendance app et références aux tâches ; Java/Kotlin JVM 17 conservés. Aucune dépendance inverse ni Android dans core. | Supprimer include et dépendance après déplacement atomique ; classes compilées par AGP/Kotlin Android. Ne pas garder sourceSets partagés concurrentement pour produire deux moteurs. |
| Tests JVM | `:analysis-core:test` demeure indépendant d’Android ; tests app existants consomment le même code. Préserver les friend paths/internal actuels. | Tests déplacés vers `app/src/test`, tâche `:app:testDebugUnitTest`, SDK/variantes AGP nécessaires. Logique pure encore testable sur JVM, mais perte du build indépendant d’Android ; imports et visibilité internal à revoir. |
| Tests Android | Restent app, dépendance vers jar core ; compilation et tests de contrats requis. | Restent app ; changement de compilation et de frontières peut déplacer l’accès internal. Aucun gain automatique de couverture UI. |
| PIT | Module JVM naturel pour campagne séparée future, sur les vraies classes de production ; pas de dépendance PIT runtime. Rien n’est configuré actuellement ici. | Compatibilité à redémontrer avec AGP/configuration actuelle. Historique plugin Android en échec ; ne pas promettre sa résolution. Harness recopiant les classes = risque de divergence et de tester un autre moteur. Un harness référençant les mêmes sources resterait un couplage/complexité à justifier. |
| CI | Remplacer chemins de tâches dans automatisations à venir ; CI docs existante inchangée en comportement. Ajouter plus tard jobs fonctionnels explicites en excluant mesures. | Unifier tâches app, mais dépendre d’Android même pour le métier ; requalification des scripts PIT/fixtures. CI actuelle docs ne valide aucune option. |
| Compatibilité | Garder packages `com.example.isitvegan`, signatures et modèles évite une migration source/ABI supplémentaire. Pas de coordonnées de publication externe établies ; scripts utilisant ancien chemin casseraient sans adaptation. | Identité applicative/version inchangée si migration correcte ; bytecode Kotlin/Android et internal réévalués. Same package ne garantit pas same module. Risque d’import collision avec façade si renommage de classes simultané. |
| Maintenance | Frontière déterministe explicite, réutilisable/testable, moteur unique. Coût : un module et distinction claire des prototypes. | Moins de modules, davantage de couplage au build Android ; vigilance permanente contre imports Context/Compose dans métier. Revenir ensuite à JVM nécessiterait une nouvelle extraction. |
| Risque de transition | Faible à modéré si renommage seul, outils/docs à inventorier ; aucune raison de changer la logique. | Modéré à élevé : déplacer code et tests, fixtures et chemins relatifs, abandon/repenser PIT indépendant. N’apporte pas de correction aux défauts de l’audit. |

**Recommandation : conserver une seule bibliothèque Kotlin/JVM, future `:analysis-core`, avec dépendance `:app -> :analysis-core`.** Son rôle mérite un nom métier ; son existence est justifiée par l’application et les tests ordinaires indépendamment de PIT. Les instructions AGENTS actuelles imposent la direction app → mutation-core : le présent document propose la cible, il ne modifie pas cette règle et n’autorise pas encore sa migration. À l’exécution d’un lot explicitement retenu, mettre à jour ensemble instructions et références pour conserver la même direction sémantique.

Ne pas renommer simultanément package, classes, statuts, protocole de session, schémas de connaissance ou formats d’export. Ne pas déplacer maintenant index/profil/recherche uniquement pour « nettoyer » le renommage : les classer et envisager ensuite un source set ou module d’expériences à partir de leurs consommateurs réels, sans casser les tests instrumentés qui les utilisent.

## Migration vérifiable proposée, lot B9 séparé

1. **Geler le périmètre fonctionnel.** Lire état Git et version, conserver changements locaux ; choisir une base après B1–B4. Inventorier `rg -n 'mutation-core'` dans settings, Gradle, docs, instructions, scripts et workflows pertinents (hors build/.gradle et rapports historiques). Les rapports historiques restent inchangés. Identifier les scripts externes non inspectables ; signaler cette limite.
2. **Baseline utile.** Exécuter les tests fonctionnels core explicitement sélectionnés, app unitaires impactés ; ne pas lancer les classes benchmark/profil par une commande globale non filtrée. Enregistrer comptes/résultats et fixtures ; vérifier les assets en lecture seule. Les 111 tests de cette passe sont une base partielle, pas une baseline universelle de migration.
3. **Renommage atomique unique.** Déplacer le répertoire `mutation-core` vers `analysis-core`, changer include/dépendance et tâches documentées ; même contenu/package/API, aucun second source set main copié. Adapter instructions AGENTS/skills concernés et docs actives avec autorisation du lot ; si des fichiers d’instructions sont hors zone modifiable, signaler la référence restante. Ne pas garder un module vide ou un alias de compatibilité sans besoin identifié.
4. **Contrôles structurels.** Vérifier un seul propriétaire pour chaque FQCN métier ; absence imports Android/Compose/ML Kit dans core, absence référence core → app, absence dépendance PIT production et absence de mutation temporaire via diff. Comparer les fichiers déplacés au contenu initial ; seules différences de chemins/configuration/docs attendues. Les deux fichiers VeganAnalyzer/UiLanguage avaient déjà des responsabilités distinctes : ne pas les fusionner sur leur seul nom.
5. **Contrôles de consommation.** Vérifier `:analysis-core:test` ciblé, `:app:testDebugUnitTest` ciblé, `:app:assembleDebug`, `:app:assembleDebugAndroidTest` ; vérifier graphes compile/runtime de l’app et chemins des ressources/assets. Compile/package démontre compatibilité de build, pas acquisition ni présence à l’écran. Rejouer sur émulateur choisi le flux nécessaire si changements autres que chemins ou risque d’intégration établi, jamais Nokia par défaut.
6. **PIT ultérieur uniquement.** Quand une campagne est explicitement demandée, suivre skill mutation-testing : branche dédiée synchronisée à la référence courante, tests ordinaires verts, configuration JVM du vrai moteur et périmètre ciblé, classes/tâches renommées. Pas de copie de moteur ni de tests dans un harness divergent. Le résultat de compilation ci-dessus ne prouve pas compatibilité PIT ; aucune campagne requise pour renommer dans cette passe.
7. **Documentation et clôture.** Mettre à jour docs architecture/guide/tests/changelog et rapport de migration, expliquer prototypes versus chemins actifs ; comparer état Git final et version initiale, ne pas commit/push sans demande. En cas d’échec, corriger la migration unique ou revenir uniquement sur ses propres changements de chemins de façon revue ; ne pas laisser deux implémentations en transition.

Critères d’acceptation : un seul moteur de production ; app le consomme ; tests core sans Android ; tests/builds ciblés verts ; protocoles et verdicts inchangés ; aucune donnée/version touchée par le renommage ; aucune affirmation PIT/runtime non vérifiée. Le renommage peut attendre après v0.7 : les défauts confirmés ne dépendent pas du nom du module.
